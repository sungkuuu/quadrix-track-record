What changed: the target leverage is no longer fixed at 2 (TARGETS = [1.5, 2]; the verifier
holds each series' target in its own table); a rulebook JSON that lists `pendingOwner` entries
is a draft that the keeper refuses outside a rehearsal and the verifier refuses under a
published line; the qeth15 series entry; qeth15 in the daily job, the dry-run job and the
freshness alarm.

Method
------
Everything ran offline: the record repository's own test doubles (a fake Binance, a fake
JSON-RPC node, throwaway repository roots), keys made inside the process, no network call,
no real key, no chain write. A finding counts only when a test in the file below reproduces
it. Every refusal shown has a control next to it (the same input without the attack passes),
so that no refusal is shown with an input that could not have passed anyway. A test that
shows a weakness is marked `todo` and asserts the behaviour that would close it: it fails
until the code changes, and the run stays green meanwhile. Each weakness below carries the
objection one could raise against it and the answer; no second, independent objection was
made in this pass.

Questions asked
---------------
1. Is anything still fixed at 2 for a 1.5 book: the trigger comparison, the genesis book,
   the reset, the verifier's recompute, the model-liquidation test?
2. Can a qeth15 line pass as qETH2X or qBTC2X, or the reverse (cross-series), and can the
   qeth15 rulebook file carry another series' rulebook or name another series' decision?
3. Can the draft guard be passed: an empty list, another JSON type, a malformed entry, the
   rehearsal flags?
4. Can the series open before 2026-10-16, or without an anchored decision that pins the
   rulebook JSON (NOT IN FORCE)?
5. Workflow: step order, the step's condition and time limit, the files "Commit records"
   stages, the failure alert.
6. Can the freshness alarm or the verifier miss qeth15?
7. What does the change do to qBTC2X, which already runs on the same files?
8. Does the public verification command against the website's copy of the record keep
   working once qeth15 has lines?

Result
------
First pass: 20 tests, 15 pass, 5 todo (five of the six weaknesses below; the sixth is shown by a
passing test of the mechanism), 0 fail; Node 22.23.1 and Node 20.15.0 gave the same result.
After the fixes in the same change (F3, F4, F5, F6 below): 20 tests, 19 pass, 1 todo (F1, which
closes when this series' inception decision is anchored), 0 fail.

No wrong level from honest inputs was found. Nothing in the arithmetic assumes 2: at 1.5 the
genesis book is {A: 1.5, C: -0.5, E: 1}, every reset and trigger trades back to 1.5, the same
bar that liquidates a 2 book (low -42%) only moves a 1.5 book, and a 1.5 book liquidates at a
deeper low (-62%). The verifier holds the target per series: qeth15 lines offered as qETH2X or
qBTC2X, qETH2X lines offered as qeth15, a qeth15 rulebook file holding the qETH2X rulebook, a
qeth15 rulebook at target 2, a qETH2X rulebook at target 1.5 and a qeth15 rulebook that names
the qeth2x decision are all stopped, and the keeper writes nothing because it runs the
verifier before it appends a line. The draft guard refuses every non-array form of
`pendingOwner` before the ledger or the exchange is read. The series does not open the second
before 2026-10-16 00:00 UTC, nor before the source has closed the first bar of that day, nor
on a decision whose effective date or pinned sha256 differs from the rulebook JSON. The daily
step, its staging of the qeth15 files, its alert lines and the freshness alarm cover qeth15,
and the live leg writes only files that "Commit records" stages. On the same bars the qBTC2X
day computation of the changed files equals that of the files the qBTC2X inception decision
pins, both verifiers accept the same qBTC2X series and both reject it with one level changed,
and the recorded qBTC2X lines verify under the changed files.

Findings
--------
F1  medium, closed by the inception decision once anchored (test 17, todo until then). The qBTC2X inception decision (anchored) pins
    keeper/leverage-index.mjs, keeper/leverage-step.mjs and scripts/verify.mjs by sha256.
    The change replaces all three while qBTC2X runs on them; nothing in the code compares
    those sha256 values, so the series continues, and the anchored text then names bytes
    that no longer run. Test 16 shows the replacement does not change a qBTC2X level. The
    test closes when an anchored decision states the re-pin (names the pinned and the new
    sha256 of each file). Objection: the level is unchanged, so nothing is wrong. Answer:
    the decision says the rules are "as implemented in" those exact bytes; a reader who
    checks the sha256 of the running files finds a difference no record explains.
    Action: the qETH1.5X inception decision names, for each of the three files, the sha256
    the qBTC2X decision pins and the new sha256, and states that the qBTC2X rule, level and
    lines do not change (test 16). Test 17 passes once that decision is in the ledger.

F2  medium, open — outside this repository (test 18 shows the mechanism). To close before
    2026-10-17 00:00 UTC.
    `node scripts/verify.mjs --base https://quadrix.finance` reads record-qeth15.jsonl and
    rulebook-qeth15.json from the website's copy of the record. The website's mirror list
    does not carry them yet. From 2026-10-17 00:00 UTC (the end of the inception day) the
    command then fails with "is anchored but record-qeth15.jsonl is missing"; with the record
    copied but not the rulebook JSON, every line fails as "a rulebook changed after
    inception", which points at the wrong cause. Objection: the website is not part of the
    keeper. Answer: the README gives this command as the public check.

F3  low, fixed in this change (test 6): the shape check now requires each entry to be an
    object with a string key, so the run ends with the exit 2 refusal. A `pendingOwner` entry that is not an object ([null]) still
    stops a live run with nothing written, but as a TypeError (exit 1, "Cannot read
    properties of null") instead of the exit 2 refusal that names the file.

F4  low, fixed in this change (test 7): the verifier now fails a line whose rulebook has a
    pendingOwner that is not an array. The verifier and the keeper disagree on a non-array
    `pendingOwner`: the keeper refuses an object as a shape error, the verifier reads
    `.length`, finds none, and accepts a published line pinned to that rulebook JSON.
    The keeper cannot write such a line; the gap is in the independent check.

F5  low, fixed in this change (test 8; code older than this change): isLocalRpc reads the
    host with a URL parser and refuses userinfo. isLocalRpc accepts
    http://127.0.0.1:1@host/ and http://localhost:1@host/, whose host is elsewhere, so
    --rpc with such a URL and --from counts as a local fork rehearsal. That unlocks the
    draft guard and the throwaway values for that run only; its lines still go to
    keeper/dryrun with a rehearsal mark, no key is read, and the published verifier fails a
    rehearsal line (test 19).

F6  low, documentation, fixed in this change (test 20). The README's --series list of the verifier
    names qbtc2x and qeth2x but not qeth15.

Noted, not counted as a finding: a draft rulebook committed before its decision is anchored
makes the daily job fail on every run (exit 2), not report NOT IN FORCE (test 19). That is
the guard's stated purpose; the job's single failure issue then stays open for all series.

How to run
----------
From a checkout of the record repository with this change and `npm ci` done, run:

  node --test --test-reporter=tap keeper/test/leverage-redteam-eth15.test.mjs

The run takes about seven seconds and needs no network. Test 16 reads the files the qBTC2X
inception decision pins from the commit it names (with the version-control tool) and is
skipped in a shallow clone.
